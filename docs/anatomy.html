Анатомия consumer-теста Pact

Что на самом деле происходит между willRespondWith(), вызовом клиента и verify(). Без подписчиков, событий и слежения за «следующей строкой»: два потока в одном процессе, один номер порта между ними.

Ничего не следит за твоим кодомPact не регистрирует hooks в PHPUnit и не перехватывает вызовы. Он знает только то, что ему передали через FFI, и то, что пришло на его порт.
Mock-сервер это отдельный потокRust-поток внутри процесса php, слушает 127.0.0.1:<порт>. Тест и сервер работают одновременно.
verify() задаёт три вопроса«все ожидания получили запрос?», «были ли лишние или неверные?», «записать json и остановиться». Ответ «нет» на первые два = красный тест.

Каждый шаг: что в коде, что на самом деле

1PHP

Описание ожидания: пока просто объект

PHP-поток
$this->builder
    ->given('latest USD->EUR exchange rate exists')
    ->uponReceiving('a request for the latest exchange rates to EUR')
    ->with($request)
ничего не происходит

InteractionBuilder складывает state, описание, запрос и ответ в PHP-объект Interaction. Ни сети, ни сервера, ни FFI. Это билдер данных, как QueryBuilder до getQuery().

2FFI

willRespondWith(): ожидание уезжает в ядро

pact-php, InteractionDriver
public function registerInteraction(Interaction $i, bool $startMockServer = true): bool
{
    $this->pactDriver->setUp();
    $this->newInteraction($i);     // pactffi_new_interaction
    $this->given($i);              // pactffi_given
    $this->uponReceiving($i);      // pactffi_upon_receiving
    $this->withRequest($i);        // pactffi_with_request + body + headers
    $this->willRespondWith($i);    // pactffi_response_status + body
    ...
    if ($startMockServer) {
        $this->mockServer->start();
    }
}
Rust: реестр

Каждый метод драйвера это вызов C-функции из pact.so. После них в памяти ядра лежит структура «pact»: список interactions с их matchingRules (регулярка для rate, формат даты, min: 1 для массива). Это ещё не сервер, это данные, с которыми сервер будет сравнивать.

pact-php здесь тонкая обёртка: своей логики сравнения у него нет вообще.

3FFI

Старт сервера: поток внутри процесса php

pact-php, MockServer::start()
$port = $this->client->createMockServerForTransport(
    $this->pactDriver->getPact()->handle,
    $this->config->getHost(),   // 127.0.0.1
    $this->config->getPort(),   // 0 = выбери сам
    'http', null
);
if ($port < 0) throw new MockServerNotStartedException($port);
$this->config->setPort($port); // 41234
Rust: mock-сервер

Ядро создаёт поток (Rust-поток, не PHP), который делает bind() на 127.0.0.1:0, получает от ОС свободный порт и уходит в accept(). Порт возвращается в PHP.

С этой миллисекунды на порту слушает обычный HTTP-сервер. Ему всё равно, кто постучит: curl, Symfony HttpClient, браузер. Он работает параллельно с твоим тестом: PHP-код идёт дальше, сервер ждёт соединений.

Почему в нашем базовом классе порт выбирается до boot кернела

Scoped-клиент бандла читает MONOLITH_API_BASE_URI при первом создании и живёт до конца кернела. Поэтому PactConsumerTestCase сам берёт свободный порт у ОС в setUpBeforeClass(), записывает его в env, бутит кернел, а потом просит ядро поднять сервер именно на этом порту. Механика та же, отличается только момент выбора числа.

4–5TCP

Вызов клиента: обычный HTTP через loopback

тест → прод-код бандла
self::getContainer()->get(ExchangeRateApiProvider::class)
    ->getLatestExchangeRate(targetCurrency: CurrencyEnum::Euro);

Клиент сериализует DTO своим PaymentServiceSerializer, берёт base_uri из env и делает POST через curl. Для него это ничем не отличается от похода в nginx.

TCP, не FFI

Пакет уходит на 127.0.0.1:41234. Rust-поток принимает соединение, сравнивает запрос с каждой interaction в реестре: метод, путь, заголовки из ожидания, тело по правилам.

Совпало: отвечает статусом и телом-примером из willRespondWith, отмечает interaction как «посещённую». Не совпало: отвечает 500 и пишет mismatch в журнал.

Как библиотека «следит», что вызов стоит следующей строкой

Никак. Порядок важен только физически: нельзя постучать в порт, на котором ещё никто не слушает. Между шагом 3 и вызовом клиента может быть sleep(10), сто других строк или запрос из другого процесса, результат тот же. Если запроса не будет вовсе, журнал останется пустым, и это вскроется на шаге 8.

6–7TCP

Ответ и десериализация

Rust отдаёт пример

В ответе ровно те значения, которые мы положили в матчеры: "rate":"0.92", "date":"2026-09-17T00:00:00+00:00". Матчеры на этом шаге не участвуют, они понадобятся провайдеру при верификации.

клиент разбирает ответ

NumberNormalizer бандла превращает "0.92" в BcMath\Number, BackedEnumNormalizer делает из "eur" enum. Если бы пример был числом 0.92, тест упал бы здесь с исключением сериализатора, ещё до verify(). Это единственное место, где проверяется «consumer умеет читать то, что обещал».

8FFI

verify(): три вопроса ядру

pact-php, MockServer::verify()
try {
    $matched = $this->isMatched();          // pactffi_mock_server_matched(port)
    if ($matched) {
        $this->writePact();                 // pactffi_write_pact_file (merge!)
    } else {
        $mismatches = $this->getMismatches(); // pactffi_mock_server_mismatches(port)
    }
    return new VerifyResult($matched, $mismatches ?? '');
} finally {
    $this->cleanUp();                       // шаг 9
}
Rust смотрит в журнал

matched = true только если каждая зарегистрированная interaction получила хотя бы один запрос и ни один пришедший запрос не остался без совпадения.

Только при true ядро пишет monolith-payment-service.json. Пишет в режиме merge: дописывает interactions в существующий файл, поэтому make pact-consumer сначала удаляет старые json.

Наш единственный assert в тесте это assertTrue($matched).

9FFI

Остановка: порт свободен

MockServer::cleanUp()
$success = $this->client->cleanupMockServer($this->config->getPort());
if (!$success) {
    trigger_error('Can not clean up mock server ...', E_USER_WARNING);
}
Rust гасит поток

pactffi_cleanup_mock_server останавливает поток и закрывает сокет. Вызов идёт в finally, то есть и при красном результате. Если тест упал до verify(), порт остался бы занят, поэтому tearDown() базового класса проверяет, слушает ли кто-то порт, и при необходимости вызывает verify() сам.

Чего здесь нет

Подписчики на PHPUnit?Нет. Pact не регистрирует ни extensions, ни listeners, ни #[Before]-хуки. PHPUnit вызывает setUp, метод, tearDown как для любого теста. Всё, что делает PactConsumerTestCase, это штатные хуки нашего класса.
Перехват HttpClient?Нет. Никаких MockHttpClient, декораторов или подмены сервисов. Клиент бандла делает реальные системные вызовы connect()/send(). Подменён только адрес в env.
Слежение за порядком строк?Нет. Ядро видит только два потока данных: что ему передали через FFI и что пришло на порт. Порядок в коде важен ровно настолько, насколько сервер должен существовать до запроса.
Логика сравнения в PHP?Нет. pact-php это обёртка над C-API. Матчинг запросов, matchingRules, формат json, merge-запись файла живут в Rust-ядре, общем для всех языков Pact.

Три прогона curl-ом, которые это показывают

Скрипт поднимал mock через builder на порту 7777, потом стучал в него curl-ом без всякого Symfony. Журнал сервера решает всё.

прогончто пришло на портжурналverify()json
1ничего#1 не посещенаfalseнет
2неверное тело → 500, затем верное → 200#1 посещена, но 1 mismatchfalseнет
3только верное тело → 200#1 посещена, mismatches пустtrueзаписан

Прогон 2 важен: лишний запрос не прощается, даже если правильный тоже был. Именно поэтому в тесте один вызов клиента на одну interaction и никаких «на всякий случай».

Команды из Makefile: что делает и когда вызывать

В монолите живут команды консьюмера, в payment-service команды провайдера, у обоих одинаковая пара для деплоя. Версию и ветку все команды берут из git сами; для брокера нужны PACT_BROKER_BASE_URL, PACT_BROKER_USERNAME, PACT_BROKER_PASSWORD, окружение задаётся PACT_ENVIRONMENT (по умолчанию production).

гдекомандачто делаеткогда вызывать
монолитmake pact-consumerУдаляет старые json (Pact дописывает в файл, а не перезаписывает), гоняет phpunit --group pact: каждый тест поднимает mock, дёргает через него настоящий клиент бандла и пишет interaction в tests/Pact/pacts/monolith-payment-service.json. Провайдер не нужен.После любых правок в tests/Pact/ или в клиентах бандла. В make phpunit не входит. ARGS=--filter только для отладки: такой json неполный.
монолитmake pact-publishСначала полный pact-consumer (фильтры сброшены принудительно), затем pact-broker publish с версией = полный sha и текущей веткой.Когда контракт изменился и провайдер должен его увидеть. Только с чистого коммита: под одним sha другое содержимое брокер не примет. В CI на каждый push.
payment-servicemake pact-provider-initСоздаёт БД payment_service_test (если нет) и гоняет миграции в test-окружении без унаследованных DATABASE_*.Один раз после make init или пересоздания postgres, и после новых миграций. Идемпотентна.
payment-servicemake pact-providerPHPUnit-тест: поднимает встроенный сервер в APP_ENV=test на свободном порту, verifier для каждой interaction делает setup state → записанный запрос → сравнение по matchingRules → teardown. С PACT_BROKER_BASE_URL контракты берутся из брокера (main-ветка консьюмера, одноимённая ветка, всё задеплоенное; pending включён) и результат публикуется; без него читаются файлы из tests/Pact/pacts.После правок в inner-api контроллерах, в ProviderState и фикстурах, и всякий раз, когда консьюмер опубликовал новый контракт. Читать: has a matching body (OK/FAILED), ниже diff по JSON-path; Pending Failures сборку не валят.
обаmake pact-can-i-deployСпрашивает брокер, совместима ли версия HEAD с тем, что записано как задеплоенное в PACT_ENVIRONMENT. Ничего не меняет, в ответе таблица версий и причина.Перед деплоем; в пайплайне это гейт в CodeBuild. «no» у консьюмера почти всегда значит: провайдер контракт не верифицировал, или верифицировал, но в это окружение не задеплоен.
обаmake pact-record-deploymentСообщает брокеру «версия HEAD теперь стоит в PACT_ENVIRONMENT»; прежняя запись для окружения перекрывается.Только после успешного деплоя и только из пайплайна. Руками лишь на локальном брокере, чтобы изобразить деплой. Без записи окружение для брокера пустое, и консьюмерам туда нельзя.
Меняется клиент в монолитеpact-consumer → pact-publish → в PS pact-provider из брокера → если красное, добавить state и фикстуру в PS, повторить.
Меняется inner-api в payment-servicepact-provider из брокера. Красное = ломаешь консьюмера, чинить до мерджа. Переименование state ломает задеплоенных консьюмеров со старым именем: старый case держать, пока такой консьюмер стоит в окружении.
Можно ли выкатывать?pact-can-i-deploy на нужной стороне с нужным PACT_ENVIRONMENT. В пустое окружение первым всегда едет провайдер.
Локально с нуляВ PS pact-provider-init один раз, дальше как выше. Для локального брокера добавить PACT_CLI_DOCKER_ARGS=--network=host.
