Pact: playbook для сервисов

Как контрактные тесты устроены у нас: что писать в консьюмере, что в провайдере, что происходит в CI и на деплое, что смотреть в брокере и на какие грабли мы уже наступили. Пилот: монолит (consumer) и payment-service (provider).

Зачем

Монолит ходит в payment-service по HTTP. Что именно он шлёт и что ожидает получить, нигде не зафиксировано: это знание размазано по клиенту в бандле, по контроллерам PS и по головам. Переименовали поле в ответе PS, монолит узнаёт об этом на staging, в лучшем случае. Интеграционных тестов между сервисами нет, а поднимать оба сервиса ради каждого PR дорого и медленно.

Pact фиксирует это знание в виде контракта: списка пар «такой запрос → такой ответ», который пишет консьюмер и проверяет провайдер. Обе проверки бегут в юнит-скорости, по отдельности, без поднятия второго сервиса. Брокер хранит контракты и результаты и отвечает на единственный вопрос, который важен перед деплоем: совместима ли эта версия с тем, что сейчас стоит на окружении.

ConsumerСервис, который зовёт чужой API. Пишет тест с ожиданием «запрос → ответ», тест гоняет настоящий HTTP-клиент против mock-сервера. Результат: json-контракт.
ProviderСервис, который этот API отдаёт. Берёт контракт, поднимает себя в test-окружении, шлёт себе записанные запросы и сравнивает ответы по правилам из контракта.
BrokerОдин на организацию. Хранит контракты по версиям и веткам, результаты верификаций, кто где задеплоен. Отвечает на can-i-deploy.

Словарь

interaction
Одна пара «запрос → ответ» в контракте. Один тестовый метод = одна interaction.
matcher
Правило вместо точного значения: regex, datetime, eachLike, like. Пример внутри matcher-а отдаёт mock консьюмеру, правило проверяется у провайдера.
provider state
Строка given('...'): предусловие, которое провайдер должен создать у себя перед проверкой (строка в базе). Переменные данные идут в params.
версия
Полный sha коммита. Под ним публикуется контракт и результат верификации. Версия в брокере неизменяема.
ветка
Метка на версии: из какой ветки она собрана. Провайдер проверяет «последнюю версию из main-ветки консьюмера», у нас main-ветка = development.
окружение
staging и production. Запись «версия X стоит в staging» делает пайплайн деплоя (record-deployment). Окружения development нет: из этой ветки ничего не деплоится.
pending
Контракт, который провайдер ещё ни разу не проходил. Красный результат по нему не валит сборку провайдера: консьюмер может описывать ожидание раньше, чем провайдер его реализует.
can-i-deploy
Вопрос брокеру: «версия X совместима со всем, что сейчас задеплоено в окружение Y?». Ответ зависит только от задеплоенных версий, не от веток.

Как устроено у нас

  1. PR или push в монолите → workflow pact-consumer.yml: make pact-consumer пишет контракт, make pact-publish публикует его в брокер под sha коммита и именем ветки (на PR: ветка фичи).
  2. PR или push в payment-service → workflow pact-provider.yml: make pact-provider забирает из брокера контракты по трём правилам (одноимённая ветка, задеплоенные версии, main-ветка консьюмера), проверяет и публикует результат под своим sha.
  3. Деплой (CodePipeline, ветка release = staging, main = production): перед сборкой make pact-can-i-deploy, после выкладки make pact-record-deployment. Этап в работе, см. план.
веткачто этокак её видит брокер
sc-xxxфичаверсии с веткой sc-xxx; провайдер проверит их, только если у него есть ветка с тем же именем (правило «одноимённая ветка»)
developmentкуда мержатся фичиmain-ветка участника: провайдер в каждом своём PR проверяется против последнего контракта отсюда
releasestagingчерез окружение staging, после record-deployment
mainproductionчерез окружение production, после record-deployment

Брокер один на все окружения, стоит в приватной сети AWS. Workflow до него достают с self-hosted раннера (переменная PACT_RUNNER), доступ из секретов PACT_BROKER_*. Пока их нет, workflow гоняют тесты и ничего не публикуют. Три схемы, где что запускается: на странице анатомии.

Consumer: как добавить interaction

Пример: монолит, tests/Pact/PaymentService/ExchangeRateApiProviderPactTest.php. Правила: один класс на один ApiProvider бандла, один метод на одну реальную форму вызова (зеркало call-site в src/), клиент берётся из контейнера через PactConsumerTestCase, подменяется только env с base_uri.

1

Запрос: точные значения, только нужные заголовки

Это наш запрос, мы его контролируем, поэтому без matcher-ов. Заголовки только те, на которые провайдер опирается (Content-Type нужен MapRequestPayload). Лишний заголовок в контракте = лишнее требование к провайдеру.

$request = (new ConsumerRequest())
    ->setMethod('POST')
    ->setPath('/inner-api/payment-service/exchange-rate/latest')
    ->addHeader('Content-Type', 'application/json')
    ->setBody(['sourceCurrency' => null, 'targetCurrency' => CurrencyEnum::Euro->value]);
2

Ответ: форма через matcher-ы, точное значение только там, где провайдер обязан его вернуть

Значение внутри matcher-а это пример: его отдаёт mock, клиент должен его распарсить. Правило (regex, datetime, «массив минимум из одного») проверяется у провайдера. Голое значение без matcher-а, как targetCurrency ниже, требует от провайдера ровно его: фильтр должен быть соблюдён.

$response = (new ProviderResponse())
    ->setStatus(200)
    ->addHeader('Content-Type', 'application/json')
    ->setBody($this->matcher->eachLike([
        'sourceCurrency' => $this->matcher->regex('usd', self::enumValuesRegex(CurrencyEnum::class)),
        'targetCurrency' => CurrencyEnum::Euro->value,
        'date' => $this->matcher->datetime("yyyy-MM-dd'T'HH:mm:ssxxx", '2026-09-17T00:00:00+00:00'),
        'rate' => $this->matcher->regex('0.92', '^\d+(\.\d+)?$'),
    ]));
3

State как предикат, переменные данные в params

Строка given описывает факт, который провайдер должен обеспечить: «latest USD->EUR exchange rate exists». Конкретные id и даты не зашиваются в строку, а передаются в params: провайдер читает их в фикстуре. Одна строка = один case в enum провайдера, см. ниже.

$this->builder
    ->given('USD->EUR exchange rates exist for a date range', ['dateStart' => '2026-09-01', 'dateEnd' => '2026-09-03'])
    ->uponReceiving('a request for USD->EUR exchange rates by date range')
    ->with($request)
    ->willRespondWith($response);
4

Вызов настоящего клиента и verify

Без вызова клиента mock никто не дёрнет и verify упадёт. Результат вызова не ассертится: сравнивать его с собственным примером бессмысленно, типы гарантирует конструктор DTO.

self::getContainer()->get(ExchangeRateApiProvider::class)
    ->getExchangeRates($dateStart, $dateEnd, null, CurrencyEnum::Euro);

$this->verifyInteractions();

Запуск: make pact-consumer. Удаляет старые json (Pact дописывает в файл, а не перезаписывает) и гоняет группу pact-consumer. Контракт в tests/Pact/pacts/monolith-payment-service.json, в git не попадает. Ни провайдер, ни брокер не нужны.

Provider: как добавить state

Пример: payment-service, tests/Pact/. Верификация сама запускает сервис встроенным сервером PHP в APP_ENV=test на свободном порту, с отдельной тестовой базой. Перед каждой interaction verifier зовёт POST /_pact/provider-states (роут только в test), контроллер чистит таблицы и создаёт данные под state.

1

Case в enum: реестр всех строк given

Строка должна совпадать с консьюмером символ в символ. Enum это единственное место, где перечислены все состояния; параметры описаны в docblock.

enum ProviderState: string
{
    case LatestUsdEurExchangeRateExists = 'latest USD->EUR exchange rate exists';
    /** params: dateStart, dateEnd (Y-m-d) */
    case UsdEurExchangeRatesExistForDateRange = 'USD->EUR exchange rates exist for a date range';
    /** params: customerId, offerId */
    case ConsentDetailsForCustomerAndOfferExist = 'consent details exist for a customer and an offer';
}
2

Фикстура в контроллере

match по enum, по одной ветке на state. Параметры через param(): отсутствующий параметр это 400 и понятная ошибка в логе верификации, а не пустая таблица.

match ($state) {
    ProviderState::LatestUsdEurExchangeRateExists => $this->addRate(CurrencyEnum::UsDollar, CurrencyEnum::Euro, '0.92', 'today'),
    ProviderState::UsdEurExchangeRatesExistForDateRange => $this->addRatesForRange(
        $this->param($state, $params, 'dateStart'),
        $this->param($state, $params, 'dateEnd'),
    ),
    ProviderState::CustomerHasNoConsentDetails => null,
};
3

Запуск

make pact-provider-init один раз: поднимает тестовый postgres из docker-compose.test.yml и гоняет миграции. Затем make pact-provider. Без брокера (нет .env.test.local) проверяются файлы из tests/Pact/pacts: скопируйте туда json консьюмера. С брокером контракты берутся из него, результат публикуется под sha и веткой из git.

Переименовать или удалить state нельзя просто так. Контракт задеплоенной версии консьюмера продолжает ссылаться на старую строку, и верификация против production падает. Сначала консьюмер перестаёт использовать строку и доезжает до прода, потом провайдер её убирает.

Что смотреть в брокере

Красный у провайдера в PR

Провайдер сломал ожидание консьюмера: ответ не прошёл правило из контракта. Лог верификации показывает interaction, поле и правило. Чинит провайдер; если ожидание неверное, чинит консьюмер и публикует новый контракт.

Исключение: interaction помечена pending. Это новое ожидание, которое провайдер ещё не реализовал; сборку оно не валит, но до реализации консьюмер этот вызов не задеплоит.

Красный can-i-deploy

Либо провайдер ещё не проверил эту версию контракта (результата нет: подождать его CI или запустить верификацию), либо проверил и она красная. Во втором случае ответ брокера называет версию провайдера и interaction.

У провайдера красный can-i-deploy значит: его версия не проходит контракт консьюмера, который сейчас задеплоен в это окружение.

В UI брокера: список контрактов пары, у каждой версии ветка и пометки окружений; матрица «версия консьюмера × версия провайдера» с результатом; фильтр по ветке и окружению. Для пилота есть своя витрина поверх API брокера: окружения с вердиктом, матрица, лента публикаций.

Релиз: кто кого ждёт

изменениебезопасно?порядок
провайдер добавил поле в ответдав любом порядке: контракт описывает только поля, которые консьюмер читает
провайдер убирает или переименовывает поле ответанет1. консьюмер перестаёт читать поле, публикует контракт, деплоится. 2. провайдер убирает поле: can-i-deploy зелёный, потому что задеплоенный консьюмер поле больше не требует
провайдер требует новое обязательное поле в запросенет1. провайдер принимает поле как необязательное, деплоится. 2. консьюмер начинает слать. 3. провайдер делает обязательным
консьюмер начинает читать новое поле, которого у провайдера ещё нетда, с pendingконсьюмер публикует ожидание из фичи, у провайдера оно pending и не валит сборку; задеплоить фичу консьюмер сможет только после реализации у провайдера

Общее правило: деплоится тот, чья версия совместима с тем, что уже стоит. can-i-deploy это и проверяет, порядок выше это способ сделать его зелёным без ручной координации.

Грабли, на которые уже наступили

  • Pact дописывает json, а не перезаписывает. Старые interaction остаются в файле. make pact-consumer чистит каталог перед прогоном; руками phpunit без этого даёт замусоренный контракт.
  • Версия неизменяема. Под одним sha другое содержимое брокер отвергает. Публиковать только с чистого коммита, после полного прогона без --filter.
  • Переименованный state ломает задеплоенную версию (см. выше).
  • Replica-соединение читало dev-базу. В PS DATABASE_REPLICA_DSN из docker-compose.override.yml перебивал .env.test: настоящие env сильнее dotenv. Сервер верификации стартует без унаследованных DATABASE_*.
  • Test-окружение PS никогда не поднималось. monolog.yaml ссылался на kafka-хендлеры, которых в test нет; .env.test не существовал. Теперь есть, вместе с when@test-переопределениями.
  • FFI только в dev-образе. pact-php работает через ext-ffi; на staging/prod он не нужен и не ставится. В CI ставится через setup-php.
  • Брокер не в репозитории. Адрес и креды только в окружении (секреты CI) или в личном gitignored .env.test.local. В .env.test только имя участника.
  • Workflow-файлы пушат только админы. Push-ruleset на .github/** в обоих репо: файлы передаются тимлиду отдельно.
  • Mock-сервер слушает только после willRespondWith(). Порт выдаёт ОС; base_uri спрашивать раньше бессмысленно.

Чеклист: подключить новый сервис

consumer
  1. ext-ffi в dev-блоке Dockerfile, образ пересобрать.
  2. composer require --dev pact-foundation/pact-php:^10, разрешить плагин composer-downloads-plugin.
  3. PACT_CONSUMER_NAME=<имя> в .env.test; группу pact-consumer исключить в phpunit.xml.dist; tests/Pact/pacts/*.json в .gitignore.
  4. Базовый класс по образцу PactConsumerTestCase и класс на каждый ApiProvider.
  5. Блок Pact в Makefile: pact-consumer, pact-publish, pact-can-i-deploy, pact-record-deployment.
  6. Workflow pact-consumer.yml (копия из монолита), передать на пуш админу.
  7. В брокере: create-or-update-pacticipant --name <имя> --main-branch development.
provider
  1. ext-ffi в dev-образ, pact-php в dev-зависимости.
  2. Рабочее test-окружение: .env.test, тестовая база в docker-compose.test.yml, when@test там, где конфиг ссылается на сервисы, которых в test нет.
  3. PACT_PROVIDER_NAME=<имя> в .env.test; группа pact-provider исключена из обычного прогона.
  4. Enum состояний и контроллер /_pact/provider-states под when@test.
  5. Тест верификации по образцу PactProviderVerificationTest: встроенный сервер, селекторы mainBranch + matchingBranch + deployedOrReleased, pending включён.
  6. Блок Pact в Makefile: pact-provider-init, pact-provider, pact-can-i-deploy, pact-record-deployment.
  7. Workflow pact-provider.yml, участник в брокере с main-веткой development.

Ориентир по времени из пилота: consumer-сторона с пятью interaction и provider-сторона с пятью state заняли по одному дню каждая, большая часть ушла не на Pact, а на то, чтобы test-окружение провайдера вообще поднималось.
